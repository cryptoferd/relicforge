UNDER THE FORGE

How Relic Forge works under the hood.

The normal Relic Forge interface deliberately hides most blockchain terminology. This page does the opposite. It explains the contract suite, storage model, mint-stage engine, reveal flow, fee accounting, randomness funding, rendering, creator authority, and the exact relationship between what a creator clicks in Studio and what happens onchain.

01 · SYSTEM MAP

One Studio, several specialized contracts.

Relic Forge separates creation, immutable project data, ERC-721 ownership, rendering, randomness, and platform-fee accounting instead of placing everything in one monolithic contract.

02 · ARTWORK & DATA

Artwork becomes immutable, addressable onchain data.

Studio preprocesses uploaded artwork into compact payloads. RelicProjectDataV1 writes artwork and collection-recipe bytes into small code-backed storage contracts. Trait records then point to a shard address plus an offset and length instead of copying the same bytes repeatedly.

Artwork shards

addArtShard(bytes) stores packed visual data. Each trait records its layer, index, name, storage pointer, byte range, encoding, and metadata-visibility flag.

Recipe / DNA shards

addDnaShard(bytes) stores the finished collection recipe table. A recipe is a compact sequence of trait indexes—one byte per layer—for a particular collection slot.

Storage ceiling

The data contract rejects any individual storage shard above 23,000 bytes. Studio currently uses a more conservative 22,000-byte single-trait ceiling so an asset cannot make it through upload only to fail during Forge compilation.

1/1 metadata

Standalone one-of-one artwork can occupy a dedicated recipe slot and carry its own token name, description, and custom attribute pairs through setOneOfOneMetadata().

03 · VALIDATION & IMMUTABILITY

The collection is checked before it is sealed.

After all artwork and recipe bytes are written, Relic Forge validates recipes in bounded batches with validateNextRecipes(). Each recipe is checked to ensure every referenced trait actually exists. Only after the validation cursor reaches the full supply can the creator call sealContent(provenanceHash).

Provenance hash

The final provenance hash is a cryptographic fingerprint of the compiled project. It provides an independent reference to the collection content that was finalized.

Content seal

Once contentSealed becomes true, ProjectData's artwork/recipe mutation functions can no longer run. The collection's render configuration is also locked because setRenderConfig() refuses changes after the data contract is sealed.

Important: sealing artwork is different from surrendering creator control. The artwork can be permanently locked while mint stages, mint pause/resume, future reveal mode, payout wallet, and royalties remain creator-controlled.
04 · MINT-STAGE ENGINE

Minting is a global gate plus independently configurable stages.

masterMintEnabled is the collection-wide safety switch. When it is false, no collector mint can succeed. Each MintPhase then provides its own schedule, price, access rules, supply cap, and wallet limit.

MintPhase fieldWhat it controls

For a restricted stage, the leaf includes the chain ID, collection address, stage ID, wallet, and allowance: keccak256(abi.encode(block.chainid, address(this), phaseId, msg.sender, allowance)). This prevents a proof from being casually reused across another chain, collection, or mint stage.

Post-launch allowlist changes

The collection contract does not store a mutable array of approved wallets. It stores the stage's merkleRoot. Because updatePhase() may replace that root while creator control remains active, a creator can add wallets, remove wallets, or change per-wallet allowances after launch without redeploying the NFT contract.

The Creator Dashboard rebuilds the V1 Merkle tree from the edited wallet list, submits the replacement root onchain, then publishes the matching wallet proofs to RelicForge Cloud. The public mint page requests the connected wallet's proof from that table. The root and proof table therefore need to stay synchronized, and Relic Forge handles them as one creator operation.

05 · REVEAL

Forge Reveal and Deferred Reveal use the same no-reroll recipe pool.

Forge Reveal

When futureRevealMode == REVEAL_FORGE, each mint batch automatically creates a randomness request for the newly minted token range. After VRF fulfillment, anyone may call processReveal(maxSteps) to finish recipe assignment.

Deferred Reveal

When the mode is deferred, minted NFTs are marked pendingDeferred instead of immediately creating a randomness request. The creator later calls requestRevealEpoch() to group the unrequested pending range into a reveal request.

Both paths eventually enter _assignRecipe(). Relic Forge uses a swap-style global pool so each recipe is consumed once. There is no creator reroll path. Large reveal ranges are processed in bounded chunks so a collection does not need one enormous transaction.

Changing futureRevealMode affects NFTs minted after the change. Already-minted deferred NFTs remain in the deferred queue and still need their pending reveal requested and completed.
06 · VERIFIED RANDOMNESS

Each collection has its own randomness budget.

The Chainlink VRF adapter maintains nativeCredit[collection]. Anyone can sponsor a collection with fundConsumer(), but a collection can spend only its own balance. The adapter quotes the current request cost before sending a request upstream.

  • quoteRequestPrice() estimates one VRF request.
  • fundConsumer(collection) adds native-token credit.
  • Insufficient credit causes the mint/reveal request to revert atomically instead of creating an unfunded reveal.
  • withdrawConsumerCredit() can withdraw unused credit only to the collection's current payout receiver.
  • Randomness callback IDs are mapped back to Relic Forge's local request sequence.
  • The VRF wrapper is chain-specific infrastructure, so each supported network can have its own adapter configuration.
  • If a verified word is recorded but delivery back to the collection fails, replayFulfillment() can retry delivery of that exact stored word. It cannot request a replacement word or reroll the result.
07 · FEES & PAYOUT ACCOUNTING

Creator proceeds and platform fees are accounted for separately.

At collection creation, the creator chooses a fee mode. In Sponsored mode the creator covers the platform cost up front. In Minter Supported mode a USD-denominated per-NFT fee can be converted into native token at mint time through the fee policy's price feed.

Creator proceeds

withdraw() sends only the collection balance that is not reserved as accrued platform fees to payoutReceiver. Anyone may trigger the function; the destination is enforced by the contract.

Reserved platform fees

withdrawPlatformFees() forwards reserved mint fees to the immutable collection fee policy. They are not sent to the creator payout wallet.

08 · RENDERING

The canonical token can always be rendered from onchain state.

The renderer exposes ERC-721 metadata plus a direct renderToken() path. A collection may optionally have a cached display endpoint for marketplace presentation, but the canonical onchain artwork remains independently renderable. If holder switching is enabled, a token owner can set that token's display preference.

Render configuration is creator-controlled only before ProjectData is sealed. Once artwork and metadata are locked, the display-policy configuration is locked with them.

11 · AUTHORITY BOUNDARIES

The creator, platform, and public callers have different powers.

Creator controller

Controls minting, mint stages, future reveal mode, payout destination, royalty settings, creator mints, and deferred-reveal requests until creator control is surrendered.

Platform fee admin

Controls platform-fee economics inside RelicForgeFeePolicyV1. It cannot modify collection artwork, token ownership, creator proceeds destination, mint stages, or reveal assignments.

Permissionless maintenance

Reveal processing, creator-proceeds withdrawal trigger, and platform-fee forwarding can be called by anyone, but the contracts enforce the destination and state transition. This keeps completion possible even after creator control is surrendered.

13 · NETWORK MODEL

The architecture is deployed independently per EVM network.

Relic Forge's application can use the same contract architecture on multiple compatible networks, but each network requires its own official Factory, Collection implementation, ProjectData implementation, Renderer, Randomness Adapter, Fee Policy, oracle configuration, and randomness-provider configuration. The application selects the correct canonical registry for the chosen chain.

The current public development build may use testing-network infrastructure. A network is not production-enabled merely because the frontend can name or connect to it; the canonical contract suite must first be deployed and configured for that chain.
